# Privacy by Design — решение для целевой архитектуры

## Контекст

На основе инвентаризации данных (см. `Task1/reports/data-inventory.md`) и аудита безопасности
(`Task1/reports/security-audit.md`) разработано архитектурное решение,
реализующее 7 принципов Privacy by Design (PbD) в целевой архитектуре Medikamente.

Целевая архитектура — микросервисная платформа на Kubernetes (K8s) с базами
PostgreSQL, ClickHouse, Elasticsearch, Victoria Metrics и шиной событий Kafka.

---

## 1. Proactive not Reactive; Preventative not Remedial

### Принцип
Архитектура должна предотвращать нарушения приватности, а не исправлять последствия.

### Архитектурные решения

| Решение | Описание | Связь с проблемой (Task1) |
|---|---|---|
| **Data Classification на этапе ввода** | Каждое поле формы маркируется тегом (PII, MEDICAL, FINANCIAL) до попадания в БД. Теги хранятся в колонке `tags jsonb` вместе с данными. | P33 — нет классификации |
| **Policy-as-Code (OPA)** | Open Policy Agent — все запросы к API проверяются политиками доступа на основе тегов. Несанкционированный доступ блокируется до выполнения запроса. | P1, P3 — нет RBAC |
| **Consent Management до записи** | Согласие на обработку ПДн запрашивается при первой записи. Без согласия система блокирует ввод PII/MEDICAL данных. | P13 — нет согласия |

### C4-реализация
- **API Gateway** (Kong / Spring Cloud Gateway) — проверка JWT + согласия перед проксированием
- **OPA sidecar** в каждом микросервисе — политики доступа на уровне запроса
- **Consent Service** — микросервис хранения и проверки согласий

## 2. Privacy as the Default Setting

### Принцип
Настройки приватности включены по умолчанию; пользователь не должен явно их включать.

### Архитектурные решения

| Решение | Описание |
|---|---|
| **Data minimization по умолчанию** | Формы содержат только обязательные поля для бизнес-процесса. Доп. поля (соц. статус, место работы) — опциональны. |
| **Обезличивание в аналитике** | ClickHouse получает только обезличенные данные (псевдоним вместо ФИО). PII остаётся в PostgreSQL. |
| **Маскирование в интерфейсах** | API Gateway маскирует ПДн в ответах: телефон `+7***12`, email `a***@mail.ru`. Полные данные — только при явном разрешении. |
| **Минимальный срок хранения** | `RETENTION:1Y` для анализов, `RETENTION:3Y` для мед. карт (по умолчанию). |

### C4-реализация
- **Anonymizer Service** — ETL-пайплайн PostgreSQL → ClickHouse с обезличиванием
- **Masking Middleware** — встроен в API Gateway, конфигурация маскирования по тегам
- **Retention Scheduler** — CronJob в K8s, удаляет записи с истёкшим `RETENTION`

## 3. Privacy Embedded into Design

### Принцип
Приватность не надстройка — она встроена в архитектуру, а не добавлена после.

### Архитектурные решения

| Решение | Описание |
|---|---|
| **Микросервисные границы по Privacy** | Patient Service (PII) отделён от Medical Records Service (MEDICAL). Доступ к PII и MEDICAL требует разных токенов. |
| **Database per Service** | Каждый микросервис владеет своей схемой/БД. Нет прямого доступа к БД другого сервиса — только через API. |
| **RBAC на уровне API Gateway** | Доступ к эндпоинтам разграничен на уровне API Gateway (роли: PATIENT, RECEPTION, DOCTOR, ADMIN, ANALYST). |
| **Шифрование на уровне приложения** | Поля с тегом `CRITICAL` шифруются на стороне сервиса перед записью в БД (AES-256-GCM, ключи в Vault). |

### C4-реализация
- **Patient Service** — ФИО, телефон, email, адрес (PII)
- **Medical Records Service** — диагнозы, назначения, результаты (MEDICAL)
- **Payment Service** — платёжные данные (FINANCIAL)
- **HashiCorp Vault** — управление ключами шифрования
- **Сервис-меш (Istio)** — mTLS между сервисами

## 4. Full Functionality — Positive-Sum, not Zero-Sum

### Принцип
Приватность не должна жертвовать функциональностью. Возможен win-win.

### Архитектурные решения

| Решение | Описание |
|---|---|
| **Дифференцированный доступ** | Врач видит полные мед. данные пациента; аналитик — только обезличенные агрегаты; администратор — только метаданные записи. Функциональность каждого пользователя не снижается. |
| **Audit Log для compliance** | Все действия с ПДн логируются в Elasticsearch. При утечке — полный трейл для расследования без отключения функциональности. |
| **Псевдонимизация в отчётах** | BI-отчёты строятся на обезличенных данных. При необходимости детализации — запрос через Approval Workflow. |

### C4-реализация
- **Approval Service** — workflow согласования доступа к полным ПДн
- **Audit Service** — приёмка событий (→ Kafka → Logstash → ES)
- **BI Service** — чтение из ClickHouse (только обезличенные данные)

## 5. End-to-End Security — Full Lifecycle Protection

### Принцип
Безопасность на всём жизненном цикле данных: сбор, передача, хранение, архивирование, удаление.

### Архитектурные решения

| Решение | Описание | Этап |
|---|---|---|
| **mTLS между сервисами** (Istio) | Все межсервисные вызовы шифрованы | In transit |
| **TLS 1.3 для внешних клиентов** | Patient Portal, Reception Portal — HTTPS/TLS 1.3 | In transit |
| **AES-256-GCM для БД** | Поля CRITICAL шифруются на уровне приложения | At rest |
| **Шифрование дисков K8s-нод** | Все ноды кластера — encrypted EBS/SSD | At rest |
| **WAL-G + pgBackRest** | Резервное копирование PostgreSQL с шифрованием | Backup |
| **Secure Delete** | При удалении — затирание данных перед освобождением блока | Deletion |
| **Tokenization платежей** | Payment Service не хранит номера карт — только токен от банка-эквайера | All |

### C4-реализация
- **Istio** — mTLS, авторизация на уровне сервисов
- **Cert Manager** — автоматическое обновление TLS-сертификатов
- **Vault** — ротация ключей каждые 90 дней
- **Token Provider** — интеграция с банком (токенизация)

## 6. Visibility and Transparency — Keep it Open

### Принцип
Архитектура должна обеспечивать прозрачность обработки данных для всех стейкхолдеров.

### Архитектурные решения

| Решение | Описание |
|---|---|
| **Audit Dashboard** | Дашборд на Kibana — все действия с ПДн, фильтр по пациенту, дате, сотруднику. |
| **Портал субъекта ПДн** | Пациент видит: какие данные собраны, кому переданы, срок хранения. Может скачать выгрузку. |
| **Data Mapping автоматически** | Data Inventory обновляется автоматически сервисом Discovery на основе схем БД и тегов. |
| **OpenAPI документация** | Все API документированы (Swagger/OpenAPI), включая политики приватности для каждого эндпоинта. |

### C4-реализация
- **Subject Access Portal** — веб-интерфейс для пациентов (отдельный микросервис)
- **Data Discovery Service** — сканирование схем БД, построение Data Map
- **Elasticsearch + Kibana** — хранение и визуализация аудита

---

## 7. Respect for User Privacy — Keep it User-Centric

### Принцип
Пользователь (пациент) — центральный элемент. Архитектура должна давать ему контроль над его данными.

### Архитектурные решения

| Решение | Описание |
|---|---|
| **Self-Service consent management** | Пациент в личном кабинете: дать/отозвать согласие на обработку, на передачу лаборатории, на рекламные уведомления. |
| **Data Portability (экспорт)** | Пациент может скачать все свои данные в машиночитаемом формате (JSON/CSV) одной кнопкой. |
| **Right to erasure (GDPR-style)** | Реализация «права на забвение»: удаление данных пациента по запросу (с юридическими исключениями). |
| **Уведомления об изменениях** | При изменении политики обработки ПДн — уведомление пациенту (email/push). |

### C4-реализация
- **Consent Service** — CRUD согласий, привязка к тегам данных
- **Data Portability Service** — сбор данных из всех сервисов, формирование архива
- **Notification Service** — отправка уведомлений об изменении политик
- **Patient Portal** — личный кабинет с разделами «Мои данные», «Согласия», «История доступа»

## Сводная таблица: Теги данных → Меры PbD

| Тег | Шифрование at rest | Доступ | Срок хранения | Маскирование в API | Обезличивание для аналитики |
|---|---|---|---|---|---|
| `PII:SENSITIVITY:HIGH` | AES-256-GCM | Только PATIENT, DOCTOR, RECEPTION | 3 года | Да | Да (псевдоним) |
| `MEDICAL:SENSITIVITY:CRITICAL` | AES-256-GCM | Только PATIENT, DOCTOR | 3 года | Нет (врач видит полностью) | Да (агрегаты) |
| `FINANCIAL:SENSITIVITY:HIGH` | AES-256-GCM | FINANCE, ADMIN | 5 лет | Номер карты → токен | Да |
| `AUTH:SENSITIVITY:CRITICAL` | Хеш (bcrypt) | Никто (только система) | До смены пароля | Н/Д | Н/Д |
| `INVENTORY:SENSITIVITY:LOW` | Нет | Все авторизованные | 1 год | Нет | Нет |

## Соответствие требованиям 152-ФЗ

| Требование | Реализация в целевой архитектуре |
|---|---|
| Ст. 18.1 — ответственный за обработку ПДн | Роль Data Protection Officer (DPO) выделена орг. структурой |
| Ст. 19 — обеспечение безопасности ПДн | TLS 1.3, mTLS, AES-256, RBAC, OPA, audit log |
| Ст. 19 — оценка вреда | Data Discovery + Risk Assessment Dashboard |
| Ст. 19 — обнаружение НСД | SIEM (Elastic) + алертинг в Victoria Metrics |
| Ст. 19 — восстановление ПДн | WAL-G бэкапы + Point-in-Time Recovery |
| Ст. 21 — уведомление РКН об утечках | Incident Response Playbook интегрирован в SIEM |
| Ст. 6 — согласие на обработку ПДн | Consent Service + Patient Portal |
| Ст. 14 — доступ субъекта к своим ПДн | Subject Access Portal + Data Portability |
