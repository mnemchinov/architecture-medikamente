# Отчёт по миграции — узкие места и рекомендации

## 1. Контекст миграции

| Характеристика | As-Is | To-Be |
|---|---|---|
| Серверная инфраструктура | Один физический сервер Windows Server | Kubernetes (K8s) кластер |
| Системы учёта | 1С:Бухгалтерия, 1С:Торговля (файловый режим) | Микросервисы (Java, Go), API Gateway |
| Данные | Excel-файлы (Patients.xlsx, Journal), сканы PDF, папки на файловом сервере | PostgreSQL, ClickHouse, Elasticsearch |
| Интеграции | OLE, email/флешки с лабораторией | mTLS, API Gateway, брокер сообщений |
| Мониторинг | Отсутствует | Victoria Metrics, Grafana, ELK |
| CI/CD | Ручной деплой | GitLab CI/CD, GitOps (ArgoCD) |
| Команда | 3 человека | 3+ человека (необходим рост) |

**Затрагиваемые компоненты:**
- Базы данных (Excel → PostgreSQL, файловая БД 1С → ClickHouse)
- Коммуникационные каналы (OLE → gRPC/mTLS, email → API)
- Серверное оборудование (физический сервер → K8s)
- Бизнес-логика (1С → микросервисы, Excel → ETL)

## 2. Выявленные узкие места по категориям

### Инфраструктура

| Причина | Описание | Влияние |
|---|---|---|
| Единый сервер → K8s | Перенос монолита с одного физического сервера в распределённый кластер требует перепроектирования сети, storage, discovery | Остановка сервисов при ошибках конфигурации |
| Сеть филиалов | Медицинские центры не имеют выделенных каналов; трафик пойдёт через интернет без гарантий качества | Латенси, потери пакетов |
| DNS / AD Legacy | AD-зависимые сервисы (1С) не работают в K8s без bridge-решений | Блокировка аутентификации |
| Capacity planning | Нет данных о нагрузке на текущий сервер (CPU/RAM/IOPS) — нельзя рассчитать ноды | Пере-/недо- provisioning |
| Нет тестовой среды | Миграция тестируется «на проде» или не тестируется вовсе | Регресс, потеря данных |

### Программное обеспечение

| Причина | Описание | Влияние |
|---|---|---|
| 1С файловый → микросервисы | 1С в файловом режиме не имеет API; миграция логики требует reverse engineering | Срыв сроков, неполная функциональность |
| Excel → PostgreSQL | ETL 30+ Excel-файлов с неявной схемой данных; качество данных неизвестно | Потеря/искажение данных |
| Legacy API без контрактов | Интеграции 1С с ККМ и бухгалтерией не документированы | Невозможность параллельной работы |
| .NET → Java разный стек | Разработчикам нужно переучиваться, инфраструктура меняется | Замедление разработки |
| Отсутствие CI/CD | Ручной деплой исключает быстрый rollout | Долгие релизы, ошибки при деплое |

### Интеграции

| Причина | Описание | Влияние |
|---|---|---|
| OLE 1С ↔ ККМ | Проприетарный протокол без альтернатив; замена требует физической замены ККМ | Остановка приёма платежей |
| 1С:Бухгалтерия ↔ 1С:Торговля | Внутренняя синхронизация между двумя 1С через OLE; при миграции одной из систем синхронизация рвётся | Расхождение данных |
| API лаборатории (email/флешки) | Неформальный обмен — нет SLA, нет контракта, нет тестовой среды | Потеря результатов, дубли |
| Миграция платежного шлюза | Переход с прямого соединения 1С→ККМ на API Gateway + эквайринг | Двойные списания, потери | |

### Персонал

| Причина | Описание | Влияние |
|---|---|---|
| Малая команда (3 чел.) | 3 человека не могут параллельно вести старую и новую системы | Выгорание, ошибки |
| Нет DevSecOps | Безопасность не встроена в процесс — миграция создаёт новые уязвимости | Утечка ПДн |
| Совмещение ролей | Те же люди пишут код, деплоят и поддерживают прод | Конфликт приоритетов |
| Нет опыта K8s | K8s — сложная система; кривая обучения минимум 3-6 месяцев | Нестабильная эксплуатация |
| Сопротивление изменениям | Сотрудники привыкли к Excel/1С; новый интерфейс вызовет отторжение | Саботаж, низкое adoption |

### Процессы

| Причина | Описание | Влияние |
|---|---|---|
| Ручное тестирование | Нет автотестов, регресс проверяется вручную или не проверяется | Пропущенные баги на проде |
| Нет CI/CD | Каждое изменение — ручной деплой через RDP на сервер | Долгие окна релизов |
| Ручной деплой | Нет rollback, нет версионирования артефактов | Невозможность отката при сбое |
| Нет мониторинга | Нельзя оценить SLA, нет алертов при падении сервиса | Длительные простои |
| Нет DRP / BCP | При сбое нет плана восстановления | Потеря данных, простой |

### Данные

| Причина | Описание | Влияние |
|---|---|---|
| Качество данных (Excel) | Дубли, орфографические ошибки, неконсистентные форматы | ETL может упасть или создать мусор в целевой БД |
| Миграция ПДн (152-ФЗ) | Перенос ПДн между системами требует согласий, уведомления РКН, шифрования | Юридические риски |
| Синхронизация старой ↔ новой БД | В период Parallel Run обе системы должны быть согласованы; нет готового CDC | Расхождение данных |
| Объём истории (5+ лет) | 5+ лет медицинских карт, сканов, финансовых документов | Долгий ETL, переполнение storage |
| Маппинг полей | Поля из Excel (ФИО одной строкой) → нормализованная PostgreSQL (first_name, last_name, patronymic) | Потеря данных при ошибке маппинга |

## 3. Рекомендации

### 3.1. Приоритизация мер

| Приоритет | Мера | Категория | Влияние | Сложность |
|---|---|---|---|---|
| **1** | **Strangler Fig** — поэтапная миграция: сначала портал (новые пациенты), потом EMR (параллельно), потом 1С | Процессы | Высокое | Средняя |
| **2** | **Parallel Run** — все новые сервисы работают параллельно со старыми не менее 1 месяца | Процессы | Высокое | Высокая |
| **3** | **Найм DevOps** (1 человек) + K8s-инженера (1 человек) | Персонал | Высокое | Низкая |
| **4** | **CI/CD** — GitLab CI + ArgoCD для деплоя | Процессы | Высокое | Средняя |
| **5** | **Branch by Abstraction** — выделение слоя абстракции для 1С, замена по модулям | ПО | Высокое | Высокая |
| **6** | **Мониторинг** — Victoria Metrics + Grafana + алерты с первого дня | Процессы | Среднее | Средняя |
| **7** | **Тестовая среда** — отдельный namespace в K8s, CI/CD прогон | Инфраструктура | Высокое | Средняя |
| **8** | **Шифрование ПДн при миграции** — Vault + TLS 1.3 для всех ETL-каналов | Данные | Критическое | Средняя |
| **9** | **CDC (Debezium)** — Change Data Capture для синхронизации старой и новой БД | Данные | Высокое | Высокая |
| **10** | **Обучение K8s** — тренинги для команды, sandbox-окружение | Персонал | Среднее | Низкая |

### 3.2. Quick Wins (0-2 недели)

1. **Мониторинг текущего сервера** — установить Victoria Metrics на существующий Windows Server для сбора метрик нагрузки → нужно для capacity planning
2. **Аудит Excel-файлов** — инвентаризация всех 30+ файлов, схем, дублей → база для ETL
3. **Обучение Docker/K8s** — записать команду на курсы (3 недели) → снижение сопротивления
4. **HashiCorp Vault** — развернуть Vault для хранения секретов старой и новой системы → единое место для ключей

### 3.3. Стратегия миграции (Strangler Fig)

```
Месяц 1:  Мониторинг, CI/CD, Vault, тестовая среда, обучение
Месяц 2:  Patient Portal (новые пациенты идут сразу в PostgreSQL)
Месяц 3:  Appointment Service + запись через портал (Parallel Run с Excel)
Месяц 4:  Patient Service + миграция PII (ETL + валидация)
Месяц 5:  Medical Records Service + EMR (миграция медкарт)
Месяц 6:  Payment Service + интеграция с банком (Parallel Run с 1С)
Месяц 7:  Замена 1С:Торговля — Inventory Service
Месяц 8:  Замена 1С:Бухгалтерия — Accounting Service
Месяц 9:  Отключение legacy-систем, полный cutover
```

### 3.4. Риски при непринятии мер

| Непринятая мера | Риск |
|---|---|
| Нет Strangler Fig | «Big Bang» миграция → гарантированный сбой и откат |
| Нет Parallel Run | Несоответствие данных, потеря записей о записи/оплатах |
| Нет найма | Выгорание текущей команды, срыв сроков |
| Нет CI/CD | Деплой — ручная операция с высоким риском ошибки |
| Нет CDC | Расхождение данных между старой и новой БД в период параллельной работы |

## 4. Выводы

Основные узкие места миграции — **организационные и инфраструктурные**, а не технологические. Ключевые риски:

1. Недостаточность команды (3 человека) для параллельного ведения двух систем
2. Отсутствие тестовой среды — единственный способ тестирования миграции — «на проде»
3. Файловый режим 1С — самый сложный компонент для миграции из-за отсутствия API и документированной логики
4. Качество данных в Excel — без предварительного аудита ETL будет давать ошибки

Рекомендуется **Strangler Fig** с 9-месячным горизонтом, параллельным ведением обеих систем и обязательным мониторингом с первого дня.
